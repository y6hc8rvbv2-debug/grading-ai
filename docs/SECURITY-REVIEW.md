# セキュリティ点検の記録（2026-10-22）

日本経済新聞（2026-10-22）の「不正アクセスに4経路」の記事にある4つの侵入経路に沿って、テスト採点ver6 を点検しました。
見つかった問題は、既存の機能を壊さない形で直しています。今後の点検もこの4つの観点で行います（CLAUDE.md の決まり）。

| 経路 | 記事の例 | このアプリで確かめたこと |
|---|---|---|
| ① 正規アプリ・API から侵入 | 正規の通信を装ってデータを持ち出す | 26 個の API の認証・学校の分離・service_role の使い方・CSRF・回数の制限・入力の検査 |
| ② 脆弱性を突く | PHP の重大な欠陥でサイトを乗っ取り | 使っている部品の既知の脆弱性（npm audit）・XSS・CSV・AI への指示の書き込み・セキュリティのヘッダー |
| ③ 管理者になりすます | 管理者の ID を奪って侵入 | 役割の決め方・権限の昇格・DB の RLS と関数の権限・ログイン |

## 直していないもの（先生の判断・設定が必要）

| 重さ | 内容 | おすすめ |
|---|---|---|
| 中 | **GitHub の `SUPABASE_ACCESS_TOKEN` は Supabase アカウント全体を操作できる鍵**。リポジトリに push できる人は、仕組みを書き換えて本番の DB に使える | ① 鍵の有効期限を短く（30日）② GitHub で、このリポジトリに push できる人を最小限に ③ 将来は検証用 DB だけに使える鍵に替える |
| 中 | 管理者の **二要素認証（MFA）** が無い。パスワードが漏れると管理者になりすませる | Supabase → Authentication で MFA（TOTP）を有効にし、管理者に設定してもらう。パスワードは12文字以上 |
| 低 | 管理者をやめた人の権限は、app_metadata を変えるだけでは消えない（設計：役割は profiles で管理） | やめた人は、Supabase → Authentication でユーザーを削除する |
| 低 | アカウントの削除・契約の変更の前に、パスワードを聞き直していない | 必要なら追加します |
| 低 | 管理者は、メールアドレスを知っている未登録の生徒アカウントを結び付けられる | 必要なら、生徒側の承認を追加します |

## 問題が無かったもの（主なもの）

- ログインなしで開ける API（決済の通知・定期処理・提出）は、それぞれ署名・合言葉・トークンで確かめている
- service_role（全校を読める鍵）はサーバーの中だけで使い、使う前に呼び出した人の学校を確かめている。ブラウザには出していない
- 生徒の実名は保存していない。他校のデータは RLS で見えない。DB の特別な関数はすべて search_path を固定し、権限を確かめている
- 画面に HTML をそのまま書き込む処理（XSS の原因）は無い。リダイレクト先を外から変えられない
- リポジトリに本物の鍵は入っていない。GitHub Actions は読み取りの権限だけで、入力値をシェルに直接埋め込んでいない
