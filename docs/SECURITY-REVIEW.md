## まだ残るもの

| 内容 | 理由・おすすめ |
|---|---|
| 二段階認証を**必須**にはしていない | 必須にすると、設定していない管理者がその場でログインできなくなるため。全員が設定したら必須にできます |
| GitHub に書き込める人は、仕組みそのものを書き換えられる | GitHub でこのリポジトリに書き込める人を最小限にしてください |
| Supabase のパスワードの長さ・ログインの回数制限 | Supabase の設定画面（Authentication）で、パスワード12文字以上をおすすめします |
| 二段階認証・招待の画面は、本物の Supabase では未確認 | 画面テストの代役は二段階認証の通信を再現しないため。DB の規則はテスト済み |

## 問題が無かったもの（主なもの）

- ログインなしで開ける API（決済の通知・定期処理・提出）は、それぞれ署名・合言葉・トークンで確かめている
- service_role（全校を読める鍵）はサーバーの中だけで使い、使う前に呼び出した人の学校を確かめている。ブラウザには出していない
- 生徒の実名は保存していない。他校のデータは RLS で見えない。DB の特別な関数はすべて search_path を固定し、権限を確かめている
- 画面に HTML をそのまま書き込む処理（XSS の原因）は無い。リダイレクト先を外から変えられない
- リポジトリに本物の鍵は入っていない。GitHub Actions は読み取りの権限だけで、入力値をシェルに直接埋め込んでいない

## 3回目（2026-10-27）：漏れても使えないようにする（多層の対策）

記事の「ゼロ知識証明」「鍵の分離（HSM）」の考え方を、採点アプリで実現できる形で実装しました。

| 対策 | 実装したこと | 効き始め |
|---|---|---|
| **A 答案の写真の暗号化＋鍵の分離** | 写真1枚ごとに使い捨ての鍵（AES-256-GCM）で暗号化し、その鍵を **AWS KMS（HSM）** の鍵で包んで保存（エンベロープ暗号化。`lib/crypto/envelope.ts`）。保存・表示・採点・提出・自動入力の資料はすべてサーバー（`/api/image`・`/api/image/upload`）を通す。暗号文には保存先を結び付け、書き換え・移動は復号に失敗する。以前の写真は管理者が「以前の写真を暗号化する」で暗号化（`/api/image/migrate`） | 先生が AWS KMS を設定してから（`docs/V6-SETUP.md` 任意5）。それまでは以前と同じく暗号化しない |
| **B 招待のメールアドレスはハッシュだけ** | `0023_invite_email_hash.sql`：平文の列を消し、SHA-256 のハッシュだけで照合 | いますぐ（検証用 DB へは自動で反映） |
| **C パスキー** | 指紋・顔認証でのログイン（`components/PasskeySettings.tsx`）。サーバーには公開鍵だけ | 先生が Supabase でパスキーを有効にし、`NEXT_PUBLIC_PASSKEY_ENABLED=1` にしてから（任意6） |
| **D 氏名欄の塗りつぶし** | 自動振り分けが見つけた氏名欄を、保存する前に塗りつぶす（`lib/redact.ts`。不自然な位置は塗りつぶさない）。写真にも採点AIにも氏名が残らない | いますぐ（新規採点のチェック。既定はオフ） |

検証：単体 131（暗号化・書き換え・移動・別の鍵・AWS KMS の代役・保存先の検査・塗りつぶしの位置）・DB（0023。平文の列が無いこと）・画面 273
（全部の写真を暗号化した環境で、AI採点・赤ペン・生徒の画面が動く／保存先は暗号文だけ／ログインしないと読めない／以前の写真の暗号化／120人分の氏名欄の塗りつぶし）。

限界（正直に）：
- 採点・表示のときはサーバーで復号するため、**サーバーそのもの（Vercel の環境変数と AWS の鍵）が乗っ取られた場合は防げない**。A が防ぐのは、DB・保存場所・バックアップからの流出
- 採点のため、写真は Anthropic に送る（D を使えば氏名欄は塗りつぶした写真）
- 完全なゼロ知識（会社が答案を読めない）は、AI 採点・先生の確認と両立しないため採っていない
- 本物の AWS KMS・本物の Supabase のパスキーでは未確認（代役でのテストだけ）
