# セキュリティ点検の記録（2026-10-22）

見つかった問題は、既存の機能を壊さない形で直しています。今後の点検もこの4つの観点で行います（CLAUDE.md の決まり）。

| 経路 | 記事の例 | このアプリで確かめたこと |

| ① 正規アプリ・API から侵入 | 正規の通信を装ってデータを持ち出す | 26 個の API の認証・学校の分離・service_role の使い方・CSRF・回数の制限・入力の検査 |

## 追加の対策（2026-10-22 の2回目。先生の指示で、おすすめをすべて実装）

| 内容 | 実装したこと | 先生の作業 |
|---|---|---|
| 管理者のなりすまし（パスワードの漏洩） | **二段階認証（認証アプリの6桁）**：設定画面「アカウント」で設定・解除（`components/MfaSettings.tsx`）。ログインでパスワードのあとにコードを聞く。DB も、設定した人は2段階目まで済まないとデータを返さない（`0022`。設定していない人は今までどおり）。管理者には設定をすすめる表示 | 管理者は設定画面で二段階認証を設定する（スマホの認証アプリが要る） |
| 大事な操作の前の本人確認 | **パスワードの聞き直し**：アカウントの削除・月額の申し込み・前払い・契約の管理の前（`verifyPassword`。違えば断り、決済画面も作らない） | なし |
| 生徒アカウントの結び付けの悪用・アカウントの有無の探り | 管理者の「配信先の登録」は**招待**になり、**生徒が自分の画面で「承認する」**と結び付く。招待のときにメールアドレスが登録済みかどうかを答えない（`0022`） | なし（生徒に「受信箱の招待を承認して」と伝える） |
| 辞めた管理者の権限が残る | app_metadata で役割・所属を変えると profiles にも反映。所属を外すと閲覧だけに下がる（`0022` のトリガー） | 完全に止めるときは、Supabase でユーザーを削除する |
| GitHub の鍵がアカウント全体に届く | verify-db が**検証用 DB だけの接続文字列（`VERIFY_DB_URL`）**を使えるようにした。接続先に検証用の ref・東京が無いと断り、パスワードはログに出さない | `docs/AUTO-PREVIEW.md` 設定1：`VERIFY_DB_URL` を登録し、`SUPABASE_ACCESS_TOKEN` を削除・無効化 |

検証：DB（`security_test.sql` に二段階認証・招待・役割の反映を追加。0022 が無いと失敗することも確認）・`verify_db_test.sh`（別の接続先を断る）・画面 264（パスワードの聞き直し）・単体 126・本番ビルド。

## まだ残るもの

| 内容 | 理由・おすすめ |
|---|---|
| 二段階認証を**必須**にはしていない | 必須にすると、設定していない管理者がその場でログインできなくなるため。全員が設定したら必須にできます |
| GitHub に書き込める人は、仕組みそのものを書き換えられる | GitHub でこのリポジトリに書き込める人を最小限にしてください |
| Supabase のパスワードの長さ・ログインの回数制限 | Supabase の設定画面（Authentication）で、パスワード12文字以上をおすすめします |
| 二段階認証・招待の画面は、本物の Supabase では未確認 | 画面テストの代役は二段階認証の通信を再現しないため。DB の規則はテスト済み |

## 問題が無かったもの（主なもの）

- ログインなしで開ける API（決済の通知・定期処理・提出）は、それぞれ署名・合言葉・トークンで確かめている
- service_role（全校を読める鍵）はサーバーの中だけで使い、使う前に呼び出した人の学校を確かめている。ブラウザには出していない
- 生徒の実名は保存していない。他校のデータは RLS で見えない。DB の特別な関数はすべて search_path を固定し、権限を確かめている
- 画面に HTML をそのまま書き込む処理（XSS の原因）は無い。リダイレクト先を外から変えられない
- リポジトリに本物の鍵は入っていない。GitHub Actions は読み取りの権限だけで、入力値をシェルに直接埋め込んでいない
